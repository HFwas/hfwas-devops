## 1. 目的

用 AI 模拟真实用户操作页面，产出**可复查**的 UX 走查结论，而不是“AI 觉得不好看”。

本标准解决三个问题：

1. AI 按什么身份、完成什么任务；
2. AI 每一步留下什么证据；
3. 结论按什么标准评分、如何分级、如何复核。

## 2. 基本原则

| 原则 | 说明 |
|------|------|
| 任务驱动 | 不以“逛页面”为目标，每次走查必须绑定具体用户任务 |
| 证据优先 | 每条结论必须引用 URL、截图、步骤编号；没有证据的结论不进入报告 |
| 区分环境 | 原型结论只代表原型；真实后端结论必须在真实栈上复现 |
| 人做决策 | AI 出问题清单与建议，产品/设计/研发决定是否修改 |
| 确定性优先 | 回归用 Playwright 断言；AI 只做探索与评审，不作为唯一门禁 |

## 3. Persona

至少覆盖以下三类；同一页面可按需增加“审批人”“运维”“无障碍用户”。

| Persona | 目标 | 典型关注点 |
|---------|------|------------|
| 首次使用的研发 | 从零创建并跑通一条流水线 | 入口是否明显、字段是否可理解、下一步是否清楚、错误能否恢复 |
| 日常使用的研发 | 运行、排障、审批、重试 | 路径是否短、状态是否清晰、日志是否容易定位、危险操作是否安全 |
| 平台管理员 | 维护任务类型、凭证、权限 | 批量效率、权限提示、危险操作确认、配置可发现性 |

Persona 不是装饰。每次走查必须写明：**身份、目标、起点、允许的操作范围、成功标准**。

## 4. 任务脚本模板

```markdown
### UX-NN · <任务名>

- Persona：<身份>
- 起点：<URL 或页面>
- 目标：<可观察的完成状态>
- 允许的操作：<点击/输入/返回，是否允许刷新>
- 成功标准：<例如进入运行详情且状态为待审批>
- 观察点：<入口、文案、反馈、错误恢复、危险操作>
```

任务脚本放在功能目录的 `test-cases.md` 中，不写在报告里临时编。

## 5. 证据要求

每次走查至少产出：

| 证据 | 说明 |
|------|------|
| 步骤截图 | 1440×900，命名 `<task>-<step>.png` |
| `actions.json` | 每步的意图、动作、目标、URL、前后观察、耗时 |
| ARIA 快照 | 每步的无障碍树，便于复查元素语义 |
| Trace | Playwright trace，可回放 DOM、网络、Console |
| 视频 | 整段操作视频 |
| Console 记录 | 错误与警告 |

`actions.json` 单步格式：

```json
{
  "task": "UX-01",
  "step": 2,
  "intent": "寻找新建入口",
  "action": "click",
  "target": "新建流水线",
  "url": "http://127.0.0.1:8099/index.html#/editor/new",
  "screenshot": "shots/UX-01-02.png",
  "durationMs": 120,
  "before": { "visibleRows": 5 },
  "after": { "editorTitle": "新建流水线", "editorJobs": 4 }
}
```

## 6. Rubric

每个任务按 1–5 分评分，必须附证据：

| 维度 | 1 分 | 3 分 | 5 分 |
|------|------|------|------|
| 可发现性 | 找不到入口 | 试错后找到 | 首屏即可发现 |
| 可理解性 | 文案/标签有歧义 | 基本可理解 | 无需猜测 |
| 效率 | 明显多余步骤 | 可接受 | 接近最短路径 |
| 反馈 | 操作后无反馈 | 反馈不明确 | 状态、结果、下一步都明确 |
| 错误预防 | 容易误操作 | 有校验但不及时 | 提交前即可发现并修正 |
| 错误恢复 | 出错后无出路 | 可返回重试 | 有明确恢复路径 |
| 一致性 | 同类操作表现不同 | 基本一致 | 完全一致 |
| 可访问性 | 无标签/键盘不可用 | 部分可用 | 语义、焦点、键盘路径完整 |

### 6.1 严重级

| 级别 | 定义 | 处理 |
|------|------|------|
| P0 | 阻断主流程，或危险操作缺少确认 | 立即修复，阻塞发布 |
| P1 | 明显增加理解/操作成本，或关键反馈缺失 | 本迭代修复 |
| P2 | 体验瑕疵，不影响完成任务 | 排期修复 |
| P3 | 建议性优化 | 记录，择机处理 |

### 6.2 结论格式

```markdown
#### FIND-NN · <一句话结论>

- 严重级：P1
- Persona / 任务：首次使用的研发 / UX-01
- 证据：`shots/UX-01-02.png`、`actions.json#step-2`
- 现象：<看到了什么>
- 影响：<对用户完成目标的影响>
- 建议：<具体改法>
- 环境：冻结原型 / 真实前端
```

## 7. 执行流程

```text
定义 persona 与任务
  → Playwright / Playwright MCP 执行
  → 采集截图、actions.json、ARIA、trace、视频
  → AI 按 rubric 评审并写报告
  → 产品/设计/研发复核
  → 修改原型或实现
  → 同一任务脚本重跑 + 回归 E2E
```

### 7.1 命令

```bash
cd frontend

# 确定性 E2E（当前为冻结原型）
npm run test:e2e

# 采集 AI 走查证据
npm run walkthrough

# 查看 trace
npx playwright show-trace test-results/pilot/trace.zip
```

### 7.2 Playwright MCP

项目根目录 `.mcp.json` 已配置 Playwright MCP：

```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest", "--headless", "--isolated", "--output-dir", "frontend/test-results/mcp", "--save-session"]
    }
  }
}
```

MCP 客户端需重启后加载服务；首次使用会请求批准。MCP 适合探索式走查，确定性回归仍用 `npm run test:e2e`。

## 8. 环境边界

| 环境 | 能证明什么 | 不能证明什么 |
|------|------------|--------------|
| 冻结原型 | 信息架构、文案、交互路径、状态覆盖 | 接口真实性、权限、持久化、真实日志 |
| 真实前端 + 后端 | 端到端行为、权限、错误码、数据一致性 | 真实用户偏好、长期留存 |

报告必须标注环境。原型结论不得直接写成“产品缺陷”。

## 9. 复核要求

- 至少一名产品/设计/研发复核报告；
- P0/P1 结论必须由人复现一次；
- 同一任务建议跑 2 次以上，排除偶发；
- LLM 评分不作为 CI 门禁，只作为 triage 输入。

## 10. 与现有规范的关系

- 原型阶段遵循 [prototype-first-standard.md](prototype-first-standard.md)；
- 测试编号与优先级遵循 [test-spec.md](../product/05-testing/test-spec.md)；
- 新增页面类功能仍须先交付冻结原型，再做 AI 走查。
