cd frontend

### 1.1 稳定性要求

- 所有用例使用 `data-go`、`data-action`、`data-overlay` 或可见文案定位，不依赖 CSS 层级。
- 每个用例失败时保留 `trace.zip`、截图和视频。
- 用例之间不共享浏览器上下文；每条用例独立 `page.goto`。

## 2. AI 走查任务

走查脚本：

```bash
cd frontend
npm run walkthrough
```

| 编号 | Persona | 任务 | 起点 | 目标状态 | 观察点 |
|------|---------|------|------|----------|--------|
| UX-01 | 首次使用的研发 | 找到并新建一条流水线 | `#/list` | 编辑器并保存 | 入口是否明显、必填项是否清楚、保存反馈 |
| UX-02 | 首次使用的研发 | 给流水线添加一个构建任务 | `#/editor/1` | 任务面板选中任务 | 「添加任务」位置、分组是否可理解、选中反馈 |
| UX-03 | 日常使用的研发 | 用运行时参数启动一次运行 | `#/list` | 运行详情 | 运行入口、参数弹窗、必填提示、提交后的状态 |
| UX-04 | 排障中的研发 | 找到失败任务的日志 | `?state=failed#/run/1/128` | 日志抽屉 | 失败原因是否可见、日志入口层级、日志可读性 |
| UX-05 | 审批人 | 处理待审批并取消一次运行 | `?state=waiting#/run/1/128` | 审批/取消完成 | 「通过」是否显眼、取消是否安全、反馈是否明确 |

## 3. 评分 rubric

每个任务按 1–5 分评分，必须附证据（步骤 ID、截图文件名、URL）：

| 维度 | 1 分 | 3 分 | 5 分 |
|------|------|------|------|
| 可发现性 | 找不到入口 | 需要试错后找到 | 首屏即可发现 |
| 可理解性 | 文案/标签有歧义 | 基本可理解，需少量猜测 | 无需猜测 |
| 效率 | 明显多余步骤 | 步骤可接受 | 接近最短路径 |
| 反馈 | 操作后无反馈 | 有反馈但不明确 | 状态、结果、下一步都明确 |
| 错误预防 | 容易误操作 | 有校验但不及时 | 提交前即可发现并修正 |
| 错误恢复 | 出错后无出路 | 可返回重试 | 有明确恢复路径 |
| 一致性 | 同类操作表现不同 | 基本一致 | 完全一致 |
| 可访问性 | 无标签/键盘不可用 | 部分可用 | 语义标签、焦点、键盘路径完整 |

### 3.1 严重级

| 级别 | 定义 |
|------|------|
| P0 | 阻断主流程，或危险操作缺少确认 |
| P1 | 明显增加理解/操作成本，或关键反馈缺失 |
| P2 | 体验瑕疵，不影响完成任务 |
| P3 | 建议性优化 |

### 3.2 报告要求

- 每条发现包含：编号、persona、任务、严重级、证据（URL + 截图 + 步骤）、现象、影响、建议。
- 区分「原型问题」与「原型简化导致的问题」，后者不得直接当作产品缺陷。
- 至少 5 条发现，其中至少 1 条 P1 或以上。
