## 3. 发现清单

### FIND-01 · 新建页预填真实数据，首次用户无法判断这是“新建”还是“编辑”

- **严重级**：P1
- **Persona / 任务**：首次使用的研发 / UX-01
- **证据**：`shots/UX-01-02.png`、`actions.json#step-2`
- **现象**：点击「新建流水线」后，页面已经填好名称「前端发布流水线」、仓库、分支、凭证，并预置 3 个阶段、4 个任务和 Sonar 参数（源码：`docs/pipeline/prototype/index.html:567-574`、`:636-639`）。页面没有「示例数据」「从模板开始」或空态说明。
- **影响**：首次用户可能误以为进入了某条已有流水线，或者直接保存一份带真实仓库地址和凭证的配置；与「新建」心智模型冲突。
- **建议**：新建页默认空画布，或明确提供「空白创建 / 从模板创建」二选一；模板必须标注「示例」并允许一键清空。
- **环境**：冻结原型

### FIND-02 · 任务市场提示“点击任务即可添加”，但点击后没有任何反应

- **严重级**：P1（阻断任务完成）
- **Persona / 任务**：首次使用的研发 / UX-02
- **证据**：`shots/UX-02-06.png`、`shots/UX-02-07.png`、`actions.json#step-7`
- **现象**：右侧面板显示「点击任务即可添加」，点击「Sonar 检查」后，阶段任务数保持 6 → 6，无 toast、无选中态、无新增任务。源码中任务项是普通 `.task-item` 按钮（`index.html:654-656`），点击处理器只处理 `data-toast`、`data-close`、`data-go`、`data-overlay`、`data-job`、`data-action`（`index.html:944-977`），没有处理 `.task-item`。
- **影响**：用户无法通过原型完成“添加任务”这一核心动作；如果真实实现沿用同样的事件结构，会直接阻断编排。
- **建议**：为任务项增加 `data-action="add-task-item"` 或在事件委托中处理 `.task-item`；添加后给出“已添加”、阶段任务数变化和新任务选中态；重复添加时提示或禁用。
- **环境**：冻结原型

### FIND-03 · 取消运行、删除流水线确认后没有成功反馈

- **严重级**：P1
- **Persona / 任务**：审批人 / UX-05
- **证据**：`shots/UX-05-19.png`（取消确认）、`shots/UX-05-20.png`（取消后）、`shots/UX-05-21.png`（删除确认）、`shots/UX-05-22.png`（删除后）、`actions.json#step-20`、`#step-22`
- **现象**：确认「取消运行」和「删除」后，弹窗关闭，但没有出现「已取消运行」「已删除」提示；`actions.json` 中两步的 `after.toast` 均为 `null`。源码里确认按钮同时带 `data-close` 和 `data-toast`（`index.html:819`、`:822`），而事件处理器先处理 `data-close` 并直接 `return`（`index.html:953-958`），永远不会执行到 `data-toast`。
- **影响**：用户无法确认危险操作是否生效，容易重复点击；取消后的运行状态也没有变化（原型未模拟状态更新）。
- **建议**：先执行成功提示再关闭，或把 `data-close` 与 `data-toast` 改为组合动作；真实实现中同时刷新运行状态/列表。
- **环境**：冻结原型

### FIND-04 · 运行参数弹窗缺少流水线名称、分支和运行编号

- **严重级**：P1
- **Persona / 任务**：日常使用的研发 / UX-03
- **证据**：`shots/UX-03-08.png`、`actions.json#step-8`
- **现象**：从列表点击某一行的「运行」后，弹窗标题只有「运行参数」，正文只有「本次运行会使用以下参数」，没有显示是哪条流水线、哪个分支、哪个 commit（源码：`index.html:811-816`）。
- **影响**：列表多行时，用户无法在弹窗内确认目标；一旦参数填错，可能把镜像发到错误流水线或环境。
- **建议**：弹窗顶部增加「运行 构建部署流水线 · main · 9f2c1ab」；提交按钮改为「运行此流水线」；高风险参数（如生产环境）增加二次确认。
- **环境**：冻结原型

### FIND-05 · 点击任务打开日志时，标题和内容不跟随任务

- **严重级**：P1
- **Persona / 任务**：排障中的研发 / UX-04
- **证据**：`shots/UX-04-15.png`、`actions.json#step-15`
- **现象**：点击第一个任务「克隆代码」后，日志抽屉标题显示「构建 / Maven 构建」，内容也是 Maven/Vite 构建日志，而不是克隆日志。源码中任务点击只设置 `data-focus="job"`（`index.html:758`），抽屉标题硬编码为 `{job:'构建 / Maven 构建'}`（`index.html:783`）。
- **影响**：排障时用户会看错任务日志，误判失败原因；这是日志功能的核心可信度问题。
- **建议**：把任务名和阶段名传入抽屉；日志内容按任务过滤；标题使用「阶段 / 任务 · 状态」。
- **环境**：冻结原型

### FIND-06 · 失败运行的全程日志显示 BUILD SUCCESS，与顶部失败原因矛盾

- **严重级**：P1（原型数据问题，真实实现必须避免）
- **Persona / 任务**：排障中的研发 / UX-04
- **证据**：`shots/UX-04-11.png`、`shots/UX-04-12.png`
- **现象**：页面顶部显示「Maven 构建失败：returned a non-zero code: 1」，但「查看全程日志」中连续出现 `BUILD SUCCESS`，没有任何失败行（源码日志为静态数组：`index.html:784-806`）。
- **影响**：用户会怀疑失败原因是否真实；日志作为排障依据的可信度下降。
- **建议**：原型按 `state=failed` 生成对应失败日志；真实实现必须保证日志来自实际任务输出，失败任务日志包含非零退出码与错误上下文。
- **环境**：冻结原型

### FIND-07 · 日志抽屉按 Esc 不关闭，与用户预期和原型说明不一致

- **严重级**：P2
- **Persona / 任务**：排障中的研发 / UX-04
- **证据**：`shots/UX-04-13.png`、`actions.json#step-13`
- **现象**：按下 `Esc` 后抽屉仍然存在；`docs/pipeline/prototype/README.md` 写明「X / 点击遮罩 / Esc」都可关闭。源码只有 click 与 hashchange 监听（`index.html:944-978`），没有 keydown 处理。
- **影响**：键盘用户被迫移动鼠标；与文档承诺不一致。
- **建议**：增加 `keydown` 监听，Esc 时清空 `ui.overlay` 并重渲染。
- **环境**：冻结原型

### FIND-08 · 失败运行缺少“查看失败日志”的直达入口

- **严重级**：P2
- **Persona / 任务**：排障中的研发 / UX-04
- **证据**：`shots/UX-04-11.png`
- **现象**：失败原因在页头，日志入口只有右上角「查看全程日志」和每个阶段的「日志」；用户需要先根据红色边框判断失败阶段，再进入日志。
- **影响**：排障路径多一步，尤其在多阶段流水线中容易点错阶段。
- **建议**：在失败原因旁增加「查看失败日志」按钮，直接打开失败任务日志；或在失败阶段卡片上提供主按钮。
- **环境**：冻结原型

### FIND-09 · 列表搜索会覆盖状态筛选结果，组合语义未说明

- **严重级**：P2
- **Persona / 任务**：日常使用的研发 / UX-03
- **证据**：`docs/pipeline/prototype/index.html:912-931`（搜索与筛选各自绑定，互不组合）
- **现象**：先选「成功」再输入搜索词，搜索处理器会把所有匹配行设为显示，不再受状态筛选约束；清空搜索后状态筛选也不会自动恢复。页面只提示「状态筛选仅作用于当前页」，没有说明搜索与筛选的叠加规则。
- **影响**：用户可能以为自己在看“成功”的搜索结果，实际混入了其它状态。
- **建议**：明确组合规则（交集/并集），在 UI 上显示当前生效的筛选条件；或让搜索也走同一过滤函数。
- **说明**：该组合行为未纳入 E2E，避免把缺陷固化为期望；E2E-PIPE-01 只覆盖单条件搜索与单条件筛选。
- **环境**：冻结原型

### FIND-10 · 删除操作与主操作同权重，列表行内按钮过多

- **严重级**：P2
- **Persona / 任务**：首次使用的研发 / UX-01
- **证据**：`shots/UX-01-01.png`
- **现象**：每行同时呈现「运行 / 编辑 / 历史 / 删除」四个文字按钮，删除与运行视觉权重接近；虽然有确认弹窗，仍增加误触风险。
- **影响**：高频操作被低频危险操作稀释，列表扫描成本增加。
- **建议**：保留「运行 / 编辑」为主操作，「历史」保留，「删除」收进更多菜单；危险操作使用红色或次级样式。
- **环境**：冻结原型

## 5. 原型简化与真实产品问题

| 类别 | 条目 | 说明 |
|------|------|------|
| 原型简化 | 添加阶段只弹 toast、不真正新增 | 不代表产品缺陷 |
| 原型简化 | 保存只弹 toast、不持久化 | 不代表产品缺陷 |
| 原型简化 | 取消/删除后状态不更新 | 但“无成功提示”是可带入真实实现的交互缺陷 |
| 原型数据 | 失败运行日志仍显示 BUILD SUCCESS | 真实实现必须用真实日志，不能沿用 |
| 可带入真实实现 | 新建页预填数据、运行弹窗缺上下文、任务日志错位、Esc 不关闭、任务项不可点 | 需要在真实页面与组件中逐项验证 |

## 6. 下一阶段建议

1. **先修原型**：FIND-02、FIND-03、FIND-05、FIND-07 是原型可点击链路的问题，修复后同一套走查脚本重跑。
2. **再验真实前端**：启动测试后端 + Keycloak，复用 persona 与任务脚本，重点验证：
   - 新建页空态与模板；
   - 运行时参数弹窗的流水线上下文；
   - 真实任务日志与失败状态的一致性；
   - 取消/删除后的状态刷新与提示；
   - 权限与租户隔离。
3. **把稳定路径固化为 E2E**：将本次 5 条原型用例迁移为真实前端用例，并保留原型用例作为 UX 回归。
4. **报告纳入功能评审**：P0/P1 发现必须在 `changes.md` 或 issue 中闭环，不能只停留在报告。
