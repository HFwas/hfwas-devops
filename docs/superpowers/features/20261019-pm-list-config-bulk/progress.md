## 第 2 轮 · 2026-10-19 22:40 · 筛选升级为字段/操作符/AND·OR/条件组

- **状态**：待评审
- **触发**：用户要求筛选支持且或等操作、支持选择字段、配置操作符，并借鉴成熟产品
- **目标**：把简单筛选弹层升级为可视化筛选构建器，覆盖字段、操作符、值、AND/OR、嵌套条件组、表达式预览与缺值校验
- **读取**：`design.md`、现有 PM 模块原型、`QuerySpec` 类型、Jira JQL、Linear Filters、Notion 复合筛选、Airtable 筛选组公开资料

### 做了什么

1. 调研 Jira JQL、Linear Advanced Filters、Notion 复合筛选与 Airtable 筛选组，确认成熟做法是「字段 + 操作符 + 值」配合「根 AND/OR + 条件组」。
2. 在 PM 模块原型中新增筛选构建器：
   - 字段来自视图配置的筛选字段；
   - 操作符按字段类型变化；
   - 根级 AND/OR 与条件组 AND/OR；
   - 条件组最多 2 层；
   - 多值 chip、区间输入、无需值操作符；
   - 预计匹配数与表达式预览；
   - 缺值条件阻止应用并汇总提示；
   - 快速筛选：我的工作项、本周到期、阻塞风险、未分配。
3. 筛选条件树序列化到 URL `f`，列表查询按树递归求值；条件 chip 展示嵌套组摘要。
4. 新增 `fpreset=advanced`、`preset=incomplete`、`filterInvalid=1` 等直达参数。
5. 新增/更新 3 张画板：高级筛选、筛选缺值、已应用筛选。

### 决策与取舍

- **决策**：采用「根 AND/OR + 条件组」而非自由嵌套。**理由**：对齐 Notion API 2 层限制与 Airtable 组内单一关系，避免表达式不可读。**未选方案**：无限嵌套或直接开放 JQL。

- **决策**：保留表达式预览但只读。**理由**：让用户确认逻辑，同时降低误操作。
- **决策**：条件树以 JSON 写入 URL `f`。**理由**：可分享、可刷新恢复，也便于映射到 `QuerySpec.groups`。

### 偏差与假设

- **ASSUMPTION**：`QuerySpec.groups` 已支持嵌套条件组，前端可直接映射。
- **ASSUMPTION**：枚举值提交前需要从显示值转换为字段 optionKey；原型用 code 直接演示。
- **ASSUMPTION**：日期「今天/本周」由后端按用户时区计算；原型用固定日期近似。
- 条件组只做一层嵌套；如后续需要更深层级，需重新评审交互与后端查询。

### 未完成 / 风险

- 原型未评审、未冻结。
- 条件组与枚举映射依赖后端 `QuerySpec` 与字段选项接口。
- 深层条件组合的可用性仍需真实用户验证。

### 下一步

### 决策与取舍

- **决策**：采用「阅读态内联编辑 + 完整编辑态」双模式。**理由**：Jira/Linear 的详情页既能快速改单字段，也能集中编辑；只做其中一种都会牺牲效率。
- **决策**：高频属性固定右栏，不散落在头部。**理由**：对齐 Plane/GitHub Projects 的属性栏模式，减少头部噪音。

- **决策**：字段保存与评论提交分开。**理由**：评论失败不应阻塞字段保存。
- **决策**：保存后把覆盖值写入 URL 参数，便于刷新与截图复现。**理由**：原型无后端，URL 是最稳定的状态载体。

- **ASSUMPTION**：服务端支持版本号/更新时间乐观锁；原型未实现冲突提示。
