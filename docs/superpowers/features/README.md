## 1. 目的

`progress.md` 回答一个用户最关心的问题：**AI 现在做到哪一步了，下一步是什么。**

它和另外三份文档的分工：

| 文件 | 回答的问题 | 更新方式 |
|------|-----------|----------|
| `design.md` | 要做成什么样、边界在哪 | 需求变化时修订 |
| `test-cases.md` | 怎么验证做对了 | 需求变化时先改 |
| `changes.md` | 最终改了什么、为什么偏离 | 实施过程中补全 |
| `progress.md` | **每一轮做了什么、验证了什么、卡在哪、下一步是什么** | **每轮追加，不改历史** |

`progress.md` 是时间线，`changes.md` 是结构化结果。不要把完整 diff、长篇设计重复写进 `progress.md`，用链接指过去。

## 2. 目录结构

```text
docs/superpowers/features/YYYYMMDD-<feature>/
├── design.md
├── test-cases.md
├── changes.md
├── progress.md          # AI 协作进度日志（每轮追加）
└── prototype/           # 前端页面类功能：高保真原型
    ├── index.html
    ├── prototype-spec.json
    ├── prototype-spec.md
    ├── README.md
    └── shots/
```

## 3. 什么是「一轮」

满足任一条件即为一轮，必须追加一条记录：

- 用户给出一条新指令，Agent 完成一次回应；
- 完成一个可独立验证的里程碑（例如“后端接口 + 测试通过”）；
- 状态发生变化（开始、阻塞、恢复、转入评审、完成）；
- 发现并修正了前一轮的错误或假设。

一次长会话中可以有多轮。**不要等整个功能做完才补日志**；每轮结束时当场写，保证用户中途打开文件就能看到进展。

## 4. 文件格式

### 4.1 文件头

```markdown
# <功能名> — AI 协作进度日志

> 日期：YYYY-MM-DD
> 版本：v1.0
> 说明：本文件为追加式日志。`版本` 表示格式版本，不随每轮追加递增；每轮记录见文末。

### 变更记录

| 版本 | 日期 | 变更说明 |
|------|------|----------|
| v1.0 | YYYY-MM-DD | 建立日志，定义每轮记录格式 |

---
```

### 4.2 每轮记录模板

````markdown
## 第 N 轮 · YYYY-MM-DD HH:mm · <一句话标题>

- **状态**：进行中 / 已完成 / 待评审 / 被阻塞 / 已回滚
- **触发**：用户本轮要求的摘要（一句话，不要复制整段对话）
- **目标**：本轮结束时应该达成什么
- **读取**：本轮实际读过的文档与代码（如 `design.md` §3、`PipelineRunService.java`）

### 做了什么

1. ……
2. ……

### 变更文件

| 文件 | 动作 | 说明 |
|------|------|------|
| `path/to/file` | 新增 / 修改 / 删除 | 一句话说明 |

无代码改动时写「仅文档」或「仅调研」。

### 验证

| 检查 | 命令 / 方式 | 结果 |
|------|-------------|------|
| 单测 | `mvn -pl pipeline-core test` | 通过 25/25 |
| 类型检查 | `npx tsc --noEmit` | 通过 |
| 手工验证 | 操作路径 + 观察结果 | 通过 / 未执行 |

只写**真正执行过**的验证。没跑的写「未执行」并说明原因，不要写成通过。

### 决策与取舍

- **决策**：……　**理由**：……　**未选方案**：……
- 没有新决策时写「无」。

### 偏差与假设

- 与 `design.md` / `test-cases.md` 不一致的地方，或 `ASSUMPTION: …`。
- 没有时写「无」。

### 未完成 / 风险

- ……

### 下一步

- **唯一动作**：下一轮最应该做的一件事。
- 需要用户确认的问题（如有）。
````

### 4.3 状态词表

| 状态 | 含义 |
|------|------|
| 进行中 | 本轮有产出，但目标尚未全部达成 |
| 已完成 | 目标达成，验证通过 |
| 待评审 | 实现完成，等待用户或独立 agent 验收 |
| 被阻塞 | 缺环境、缺数据、缺决策，无法继续 |
| 已回滚 | 本轮改动被撤销，需说明原因 |

## 5. 写作规则

1. **只追加，不改历史。** 发现上一轮写错，在新一轮写「更正第 N 轮：……」，保留原记录。
2. **每轮必有「下一步唯一动作」。** 让新的 Agent 或用户不必读完整对话就能继续。
3. **区分事实与推断。** 验证结果、命令输出是事实；猜测写进「偏差与假设」并标 `ASSUMPTION`。
4. **链接优先。** 文件用相对路径，设计细节指向 `design.md`，不要复制大段内容。
5. **不写聊天记录。** 只保留目标、动作、证据、决策、下一步。
6. **不写敏感信息。** 令牌、密码、真实客户数据、内网地址一律不出现。
7. **重要决策要晋升。** 影响架构或验收的决策，除了写进本轮记录，还要回写 `design.md` 或 `changes.md`；`progress.md` 只保留时间线。
8. **同一轮内多次小改不拆轮。** 按“可验证的里程碑”拆分，不按工具调用次数拆分。

## 6. 业界依据与本仓库取舍

2026-10 调研的四类成熟模式：

| 模式 | 代表 | 做法 | 本规范取舍 |
|------|------|------|-----------|
| Agent 记忆库 | [Cline](https://github.com/cline/cline) Memory Bank 约定 | `activeContext.md` 记当前焦点，`progress.md` 记已完成/进行中/待办，`decisionLog.md` 记决策 | 采纳：每轮写状态、下一步、决策；不引入多文件记忆库，功能目录只加一份 |
| 故事文件内的开发记录 | [BMAD Method](https://github.com/bmad-code-org/BMAD-METHOD) | 只允许 Agent 改 Story 文件的固定区块：任务勾选、Dev Agent Record、File List、Change Log、Status | 采纳：固定模板 + 变更文件清单 + 状态字段；避免 Agent 乱改设计正文 |
| 跨会话交接 | [Session Handoff](https://www.thepromptindex.com/skill/443-state-management-across-sessions) 实践 | 追加式日期日志，写清 Done / Unverified / Next single step，强调“验证过”与“推断”分开 | 采纳：验证表 + `下一步唯一动作` + 只追加 |
| 决策记录 | [ADR](https://www.braingrid.ai/blog/architecture-decision-records-for-ai-coding-agents) | ADR 只记稳定、难以逆转的决策，已接受的 ADR 不修改，只能被新 ADR 取代 | 采纳：轻量决策进本轮记录，重大决策晋升到 `design.md` / `changes.md` |

不采用的做法：

- 不把整段对话或工具调用流水贴进仓库；
- 不维护独立的 `activeContext.md`、`decisionLog.md` 多文件体系，避免功能目录膨胀；
- 不用 `progress.md` 代替 `changes.md` 或测试报告。

## 7. 检查清单

每轮结束前确认：

- [ ] 轮次编号连续，时间戳真实。
- [ ] 状态用词来自第 4.3 节词表。
- [ ] 变更文件与实际 diff 一致。
- [ ] 验证结果与实际命令输出一致，没跑的标「未执行」。
- [ ] 决策写了理由和未选方案。
- [ ] 偏差与假设已标注。
- [ ] 写了「下一步唯一动作」。
- [ ] 没有敏感信息。
